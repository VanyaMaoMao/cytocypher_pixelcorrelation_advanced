**Пошаговый план исправления Cytocypher для Codex**

Дата: 5 октября 2026 года. Назначение: последовательные небольшие изменения с проверкой регрессий, полное удаление AFC, сохранение QC и определения полярности, надёжный расчёт частоты сокращений.

Репозиторий: https://github.com/VanyaMaoMao/cytocypher_pixelcorrelation_advanced

Исходная точка аудита: `176e490bfa0710ee01d1daa5e1c1a2fa16377edb`.

План основан на аудите 2 октября. Локальный checkout на момент подготовки остаётся на этом commit; актуальная удалённая ветка повторно не загружалась. Codex должен сверить свою версию перед работой. Номера строк из аудита не считать стабильными: искать функции по имени.

Здесь перечислены будущие работы. Ни один шаг исправления кода этим документом не объявляется выполненным. Абсолютной гарантии отсутствия новых ошибок нет; контроль обеспечивают ограниченный scope каждого шага, воспроизводимые проверки, журнал изменений результатов и возможность отката.

**Как выполнять план**

Один шаг — одна небольшая задача с собственным результатом проверки; при необходимости несколько маленьких коммитов. Не объединять удаление AFC, изменение времени, подбор порогов и переработку QC в один большой patch.

Для каждого шага Codex выполняет цикл:

1. Проверить HEAD, рабочее дерево и завершённые зависимости.
2. Воспроизвести дефект или зафиксировать существующее поведение затрагиваемого участка.
3. Добавить проверку ожидаемого правильного поведения, если меняется измерение или исправляется дефект.
4. Внести минимальную правку в пределах шага.
5. Запустить соответствующие тесты и общий небольшой regression-набор.
6. Проверить diff, входные checksums и изменения численных результатов.
7. Обновить журнал прогресса и сохранить проверенное состояние в Git.

Не нужны отдельные пользовательские подтверждения каждого обратимого действия. Если поручен один шаг — завершить его и отчитаться. Если поручена последовательность шагов — продолжать автоматически при прохождении критериев. Остановить только зависимую часть при неизвестной семантике данных, отсутствии необходимой разметки или необъяснимой регрессии; независимые разрешённые задачи можно закончить.

Три класса изменений:

| Класс | Пример | Что должно происходить с результатом |
|---|---|---|
| Сохранение поведения | Удаление AFC-интерфейса, перенос функции, удаление действительно мёртвого кода | Принятые обычные события, времена и метрики на контрольных файлах не меняются. |
| Исправление ошибки | NaN больше не сжимает время, исправлен знаменатель, исчезли дубли | Меняются только результаты, затронутые доказанной ошибкой; есть тест с известной истиной. |
| Изменение метода | Новый детектор, новая дедупликация, новые правила полярности/QC | Требуются отдельные сравнения и валидация; новый результат не считается верным только потому, что он отличается от старого. |

Baseline текущего алгоритма — средство выявить изменения поведения, а не научный ground truth. Нельзя сохранять известную ошибку ради совпадения snapshot.

**Шаг 00. Исходное состояние и рабочая ветка**

Цель: понимать, какую версию исправляем и какие изменения принадлежат пользователю.

Действия: прочитать README, локальные AGENTS.md и инструкции репозитория; записать текущий SHA; сравнить с audited commit, если он доступен. Проверить `git status`; не перезаписывать незакоммиченные пользовательские правки. Создать отдельную рабочую ветку. Зафиксировать версии Python и библиотек, команду запуска и доступные fixtures. Не устанавливать новые версии зависимостей одновременно с изменением алгоритма.

Создать `docs/refactor_progress.md` с таблицей шагов: status, commit, выполненные проверки, ожидаемое изменение результата, известные блокеры. Использовать статусы `pending / in_progress / done / blocked`, не отмечать шаг done по факту создания файла или написания кода без проверки.

**Проверка:** текущий CLI импортируется и запускается на простом синтетическом workbook; входной файл сохраняет checksum. Если текущая версия уже отличается, обновить карту дефектов и не применять старые выводы механически.

**Не менять:** алгоритм, пороги, зависимости, результаты.

**Шаг 01. Минимальный набор проверок и baseline**

Цель: до первых существенных изменений получить механизм обнаружения регрессий.

Добавить dev-зависимость pytest и небольшой CI job либо эквивалентный воспроизводимый запуск. Не добавлять тяжёлую инфраструктуру. Синтетические Excel генерировать во временной директории теста, с фиксированными seeds; эталонные времена событий известны из генератора. Бинарные DOCX/XLSX не сравнивать побайтово: проверять смысловые таблицы и метрики.

Начальный набор: чистые регулярные пики обеих полярностей; пик на границе строки; одинаковая запись при разбиении 125/250/500 samples; internal NaN; gap; overlap; отсутствие Begin; различие duration; ERROR/REJECT; один и тот же rescue в двух экспортных источниках; uppercase extension.

Исторический контрпример: fs=250 Hz, 10 s, Gaussian peaks A=0,2, sigma=0,020 s, centers `0.125 + 0.25*k`, k=0…39, noise SD=0,0005, RNG=42. При строках 125/250/500 samples в аудите получено 36/24/21 событий, все QC PASS. Для новой версии ожидается 40 с совпадающими временами в пределах заранее выбранного допуска, а не просто одинаковое неправильное число.

Если воспроизведённые ещё не исправленные дефекты временно оформлены как `xfail`, только strict, с ID дефекта и запланированным шагом. Нельзя превращать неожиданный новый failure в xfail или считать набор с ними готовым к релизу.

**Готово, когда:** baseline сохранён отдельно от ground truth; известные ошибки воспроизводятся; обычные проверки работают локально и в CI. Реальные fixtures использовать только с разрешением на их хранение; отсутствие данных записать явно.

**Шаг 02. Входной файл никогда не должен стать выходным**

Основные места: `run_pixel_analysis.py`, `workbook.py`, output writers.

Заменить `.replace('.xlsx', ...)` централизованным построителем путей через `Path`. Проверять допустимое расширение без зависимости от регистра. До первой записи убедиться, что ни один output не указывает на input, outputs не конфликтуют между собой; учесть resolved paths и, где применимо, `samefile`. Выходной каталог задаётся явно или предсказуемо выводится из входа. Существующий input запрещено перезаписывать даже с флагом overwrite результатов.

Писать каждый output во временный файл подходящего формата в целевом каталоге, затем завершать заменой готового файла. Это атомарность одного файла, не всей группы отчётов: при частичном сбое явно сообщать, какие outputs завершены. Не печатать «всё сохранено» до завершения записи.

**Проверки:** `.xlsx`, `.XLSX`, пробелы, несколько точек в имени, directory с `.xlsx` в названии, input/output collision, повторный запуск, ошибка сохранения. Везде checksum input неизменён. Искусственно прерванная запись не оставляет повреждённый финальный output вместо прежнего корректного.

**Не менять:** детектор и численные результаты. После этого шага любые дальнейшие интеграционные тесты запускаются безопасно.

**Шаг 03. ERROR и REJECT не равны 0 BPM**

Места: `_run_auto_segment_analysis`, ветки отказа analysis, summary/reporting/plotting.

Ввести явный status и отдельные поля принятого и диагностического результата. Исключение выполнения → ERROR с типом и понятной причиной; ожидаемый отказ QC → REJECT; принятая frequency отсутствует (`None` в JSON, пустая числовая ячейка в XLSX). Найденные предварительные кандидаты можно хранить для диагностики без превращения в подтверждённую частоту.

На этом шаге не переписывать QC-критерии: сохранить текущие решения pass/reject, изменить представление ошибки. Отличать flat trace с неопределённой чувствительностью от доказанного отсутствия событий: не присваивать PASS/0 автоматически каждому ровному массиву. Если ноль действительно валиден по принятому контракту измерения, сохранять 0 отдельно от null.

Batch должен продолжать обработку остальных сегментов и сообщать о частичном сбое. Полный crash не маскировать. Предлагаемый контракт exit codes: 0 — анализ выполнен без runtime/input errors, даже если есть научные QC REVIEW/REJECT; 1 — частичный/полный runtime или output error; 2 — неправильный CLI/input contract. Зафиксировать семантику в tests.

**Проверки:** специально вызванное исключение, QC reject, корректный положительный результат, пустой файл, batch good+bad. Никакой ERROR/REJECT не попадает в численные групповые средние как 0.

**Шаг 04. Падение при отсутствии Begin**

Место: `preprocessing.build_concatenated_signal`, fallback с `re.match`.

Добавить недостающий импорт и короткий regression test. На этом шаге не менять временную модель fallback. Сохранить явный признак, что время было выведено из предположений; исправление NameError не доказывает, что такое время соответствует эксперименту.

**Проверки:** вызов с y-колонками и без Begin больше не падает с NameError; существующий путь с Begin не меняется. Если формат без Begin не обеспечивает абсолютную временную ось, в дальнейшем шаг 08 должен сделать такой режим явным/ограниченным.

**Не делать:** придумывать значения Begin или называть concatenation-time физическим временем без подтверждения схемы.

**Шаг 05. Удалить пользовательский AFC-путь**

Места: CLI, public exports, README/examples, workbook orchestration.

Удалить AFC CLI options и пользовательский вызов AFC workflow; убрать AFC из обычных outputs. Переименовать пользовательский отчёт в contraction frequency analysis. Старые AFC-флаги должны давать понятную ошибку об удалённой возможности, а не молча игнорироваться. Обновить документированные команды.

Пока допустимо оставить недостижимую AFC-реализацию до шага 06. Это короткая промежуточная стадия, не итог релиза. Не удалять старые пользовательские AFC-файлы и не переписывать историю Git.

**Проверки:** стандартный CLI работает; AFC-путь больше нельзя включить; auto-only events, timestamps, polarity и QC на контрольных валидных файлах совпадают с предыдущим шагом. Допустимы изменения имён output и нейтральных подписей.

**Не менять:** ordinary main/rescue detection. Rescue в этой версии восстанавливает обычные граничные сокращения и не является AFC.

**Шаг 06. Удалить AFC-реализацию**

Удалить `afc_review.py`, AFCReviewConfig, AFC dataclasses, AFC-only candidate/recompute/merge/assignment functions, session JSON и AFC CSV export, review plots и sections отчётов. Убрать соответствующие импорты. Проверять принадлежность helper к AFC по вызовам, а не только имени.

`min_secondary_prom` сейчас используется ordinary detector. Если он сохраняется на переходном этапе, переименовать с неизменным значением и использованием либо оставить до снятия legacy; не вырезать используемый threshold вместе с AFC. Общие функции export сохранить, если они потребуются обычному events workbook.

**Проверки:** package import, CLI smoke test, численное совпадение auto-only results с шагом 05, отсутствие AFC в public API/config/outputs. Поиск `AFC`, `aftercontraction`, `secondary` — вспомогательная проверка: текст исторического changelog допустим, а используемая нейтральная логика не удаляется лишь ради нулевого grep.

**Откат при регрессии:** выяснить общую зависимость, вернуть только неправильно удалённый reusable helper, закончить отвязку; не восстанавливать весь AFC пользовательский путь как скрытый workaround.

**Шаг 07. Убрать мёртвые правила без изменения метода**

Проверить call graph, public API и динамические обращения перед удалением. Кандидаты: невызванные prune-функции, `_candidate_orientation_sanity_score`, неиспользуемые config fields, фиктивные debug stages. Удалить ложные настройки или сохранить краткую документированную миграцию для внешних пользователей.

Не удалять работающий код из-за того, что он выглядит сложным: изменение метода начинается позже. Не переносить все числовые константы в огромный config ради формальной «чистоты».

**Проверки:** на baseline наборе не меняются события, polarity, QC и метрики; исчезают только неработающие настройки/поля. Каждый оставшийся публичный параметр должен реально влиять на заявленный участок или быть документированным metadata.

**Готово, когда:** config и debug больше не обещают фильтры, которые не выполняются. Этот шаг — отдельный commit от нового детектора.

**Шаг 08. Контракт входного Excel и частоты дискретизации**

Место: `load_cytocypher_excel`; документ `docs/input_schema.md`.

На реальных примерах/документации установить семантику Begin, Begin (seconds), End, отрицательных y-offsets и transient windows. Подтвердить, что overlap-строки содержат совместимые измерения одной записи: разные reference-кадры PixelCorrelation могут ограничивать корректность blending. Не считать похожие имена колонок взаимозаменяемыми без проверки.

Парсер должен проверять обязательные колонки, числовые y-offsets и их порядок, повторные позиции, значения fs, единицы времени, Sample ID. Согласованные повторяющиеся fs принимаются; отсутствующий fs требует явного override или документированного metadata-source. Нулевые, отрицательные, бесконечные fs отклоняются. Конфликтующие fs/timing metadata нельзя молча заменять первым значением.

Явный override хранить вместе с исходным значением, причиной и источником. Несколько Sample IDs на одном листе не сводить молча к первой/самой частой строке: обрабатывать по документированному контракту либо отмечать ошибку.

**Проверки:** перестановка y-колонок не меняет signal после корректного numeric ordering; duplicate offsets, нечисловые значения и несовместимые timing aliases дают объяснимую ошибку. Валидный workbook читается без изменения samples.

**Зависимость:** если реальных файлов/документации недостаточно, пометить точную неоднозначность. Не выдумывать формат. Исправления общего validator можно закончить, но зависимый временной адаптер не объявлять подтверждённым.

**Шаг 09. NaN не должен удалять временную позицию**

Ввести представление samples с исходными offsets, finite/observed mask и provenance. Не использовать `tr[~np.isnan(tr)]` для восстановления физического времени. Infinity — не обычное измеренное значение. Trailing padding удаляется только по подтверждённой схеме длины окна; одинаково пустая колонка не обязательно означает отсутствующий временной sample во всех форматах.

Внутренние пропуски сохраняют положение. Для минимального первого исправления не интерполировать их для детекции; отмечать invalid и разбивать на finite blocks. Временная короткая интерполяция допустима позже только как явно выбранная политика с сохранением маски и запретом выдавать synthetic samples за observed.

До адаптации legacy detector несовместимый сегмент лучше пометить REVIEW/REJECT с причиной, чем передать NaN в функции, которые на него не рассчитаны, или снова сжать время.

**Проверки:** `[0,1,NaN,2,0]` сохраняет пять позиций; событие после gap имеет прежний timestamp; leading/trailing padding и internal missing различаются; исходный raw trace сохраняется. Маски и временные массивы одинаковой длины.

**Шаг 10. Сшивка, overlaps, gaps и coverage**

Построить абсолютную timeline по контракту шага 08. Разбиение на исходные строки больше не определяет valid blocks. Block заканчивается из-за реального разрыва наблюдения/повреждения, а не границы Excel-строки.

Для overlaps задать детерминированное объединение одинаковых samples и измерение residual между перекрывающимися наблюдениями. Начать с простого проверенного правила; отдельная новая коррекция baseline между строками требует собственного сравнения. Не добавлять crossfade/масштабирование без доказанной необходимости. Поддержать вложенные и повторные окна либо явно их отклонять с причиной, не удваивать их длительность.

Gaps остаются missing. Для каждого интервала хранить observed duration и coverage. Все последующие шумовые/трендовые/периодические оценки работают по валидным участкам, не по искусственно соединённому trace. Заменить `np.empty` transient ID vector на определённый sentinel; provenance overlap может иметь несколько source rows.

**Проверки:** неперекрывающиеся окна, одинаковый overlap, конфликтующий overlap, nested windows, reordered rows, точный стык, большой gap. Измеренная длина и union покрытия совпадают с известной моделью. Не происходит событий или IBI через unknown gap. Уже на уровне построенного signal различные эквивалентные разбиения дают одинаковую timeline и значения.

**Готово, когда:** документированы duration convention, rounding tolerance и правила coverage; неизвестная семантика не маскируется interpolation.

**Шаг 11. Канонические события, полный debug и Sample ID**

Места: results, `_build_peak_debug_rows`, `build_events_dataframe`, `_collect_main_events_table`, summary exporters.

Ввести единый результат сегмента и реестр кандидатов. Минимальные поля: candidate/event ID, segment ID, source row provenance, sample index, time, amplitude, prominence, width, detection source, decision status/reasons. Разные способы обнаружения одного и того же sample-кандидата объединяют provenance, а не создают новые события. Близкие разные samples ещё не объединяются здесь: это задача дедупликации.

Rescue, отсутствующий в initial raw set, тоже обязан присутствовать в реестре. Экспортировать accepted events из одного списка, не достраивать их повторно из meta. Если `_collect_main_events_table` после удаления AFC больше не нужен, удалить его вместо ремонта ненужного пути; обязательная проверка отсутствия дублей остаётся для нового обычного export.

**Проверки:** исторический пример 19 событий/9 rescue имеет ровно 19 event rows и все 19 в audit; N совпадает с числом уникальных accepted IDs. В rejected сегменте preliminary events не выдаются как accepted. Sample ID проходит от parser до каждой итоговой таблицы. Report не меняет features события.

**Не менять:** критерии принятия пиков. Изменения количества строк допустимы только за счёт устранения представительных дублей; не объединять близкие реальные события по грубому округлению времени.

**Шаг 12. Один модуль метрик и один знаменатель**

Создать единый расчёт на основе принятых событий, валидных блоков и policy покрытия. Хранить `recording_span_s`, `observed_duration_s`, `analyzed_duration_s`, `coverage_fraction`, `duration_source`. Принять единый half-open sample convention либо другой явно описанный; timestamp span и sample coverage — разные величины.

Основные показатели: `count_rate_hz=N/analyzed_duration_s`, BPM=60×Hz; отдельно `median_ibi_rate_hz=1/median(valid_intervals)`, IBI CV и число интервалов. IBI не строить между разными blocks, через unknown gaps или исключённые интервалы. Для нескольких blocks count-rate агрегировать по суммарному count/time, не усреднять block-rates с одинаковым весом. Median IBI определять по допустимым интервалам с явно указанной схемой pooling.

Наблюдаемые настоящие паузы остаются в analyzed duration. При исключении повреждённого участка честно указать, что rate относится к оставшемуся времени. Если неполное покрытие не позволяет оценить всю запись, full-recording rate отсутствует. В экспорте выбранных transient-окон нельзя автоматически объявить union окон всей исходной записью.

Убрать hard-coded `recording_s=10`, `stim_hz=1`. CLI overrides, если нужны, должны быть явными и проверенными на соответствие данным. Stimulation frequency не участвует в подгонке детекции. Старую метрику detected/expected удалить либо обозначить как описательное отношение, без claims capture efficiency.

**Проверки:** 20 событий/20 s =1 Hz=60 BPM во всех выходах; recording override 10 s при подтверждённых 20 s вызывает конфликт, не молчаливые 120 BPM. Проверить паузы, gaps, один/ноль/два events, несколько blocks. Null не превращается в 0. Принятые timestamps не меняются от открытия отчёта.

**Шаг 13. Согласованные графики и отчёты**

Показывать исходный/обработанный trace, accepted и ambiguous peaks, missing/artifact intervals, status/reasons, duration/coverage, Hz/BPM. Получать все числа из результата шага 12. Prominence threshold не рисовать как абсолютную горизонтальную height-line: убрать вводящую в заблуждение линию или показать prominence отдельно.

В графике разрывы не соединять сплошной линией, создающей видимость измеренных значений. Подпись времени должна отражать абсолютное/локальное время. Известные invalid зоны видны пользователю. На ERROR/REJECT не показывать 0 BPM как измеренный результат. Подписи polarity/confidence временно должны быть честно описательными; новый margin будет добавлен в шаге 17.

**Проверки:** численные assertions summary↔report↔events; визуально проверить несколько примеров с gap, inverted, rejection и плотными peaks. Проверить, что отчёт помещается и подписи читаются. Нельзя считать screenshot-тест заменой проверки чисел.

**Шаг 14. Экспериментальный глобальный детектор**

Только development путь, например отдельный `detect_events_v2(recording, config)`. Старый валидный путь пока остаётся для сравнения; не возвращать его результат автоматически при неудаче v2. Сравнение должно явно обозначать версии методов.

Для каждого непрерывного валидного блока искать permissive candidate set без разрезания на transient rows. Измерять признаки одинаковым способом. Сохранять fs/time conversion и общую eligibility mask. Граница исходной строки не создаёт guard interval; реальная граница блока может делать peak неполным и требующим REVIEW. Одиночный краевой максимум не добавлять искусственным padding как уверенное событие.

Шум, detrending и smoothing выполнять внутри blocks; параметры задавать в физических единицах с проверкой достаточности дискретизации. Короткие blocks не должны получать бессмысленные большие окна фильтра. `find_peaks` distance на candidate-этапе не должен удалять полезные соседние peaks до оценки формы.

**Проверки:** peak ровно на Excel-boundary находится; candidate times/features одинаковы при эквивалентном разбиении; gap не генерирует событие; known 1/2/4 Hz candidates обнаруживаются; положительный и отрицательный signal проверяются пока с явно заданной полярностью.

**Готово, когда:** candidate generation инвариантна экспорту. Это ещё не утверждение готовности полного v2 detector или новых thresholds.

**Шаг 15. Одна финальная дедупликация**

Заменить каскад повторных dedup/recover правилами над каноническими кандидатами v2. Удаление одной вершины должно иметь reason и сохранённый competing candidate ID. Не использовать transient ID, число строк или ожидаемый stimulus count как признаки отдельного сокращения.

Разделять maxima одного broad transient и разрешимые отдельные contractions по времени, width и разделяющей valley в согласованных единицах. Зафиксировать поддерживаемый диапазон частот/ширин; не использовать универсальную 0,28 s границу. Неполная временная разрешимость → REVIEW, а не произвольная физиологическая классификация.

Разрешение пар должно быть детерминированным. Проверить цепочку A–B–C: попарная близость A–B и B–C не доказывает, что A и C — одно событие. Не усреднять timestamps двух независимых сокращений. Указать, по какому критерию выбирается представитель настоящего дубля.

**Проверки:** равные близкие пики с глубокой долиной; shoulder; broad plateau с ripple; narrow artifact рядом с нормальным peak; цепочка из трёх peaks; fast regular rhythm. Один и тот же trace при 125/250/500 samples/row должен дать 40 событий в известном контрпримере. Отдельно сверить времена, не только число.

**Не делать:** возвращать подавленные peaks через новую скрытую rescue-ветку ради прохождения одного теста. Исправить основное правило.

**Шаг 16. Два прохода без жёсткой амплитудной полосы**

Первый проход выделяет high-quality seeds по prominence/local noise, допустимой форме и отсутствию технических артефактов. Второй оценивает весь candidate set, включая не прошедших seed-порог. Опорные значения получать устойчиво; недостаток seeds/несколько популяций → явная неопределённость.

Не использовать global maximum как обязательный anchor. 70% устойчивого reference допускается только как исследуемый вариант seed selection, сравниваемый с более простой схемой. Median ±15% — diagnostic warning, не обязательное удаление. Нет общего upper-amplitude cutoff без независимых artifact features. Не возвращать события в настоящие паузы только ради регулярности.

Сначала выбрать простой noise estimator и документировать его; сравнить альтернативу только если есть конкретный провал. Пороги в versioned profile; не добавлять десятки эвристик по отдельным файлам. В этом шаге допустимо обновление ранее извлечённых feature windows, но оно должно быть единым и отражаться в сравнении.

**Проверки:** одиночный высокий artifact; amplitude alternation 1/0,65; постепенное ослабление; редкое высокое contraction; clean weak trace; pure noise; истинная пауза. Для масштабирования signal и noise вместе проверить согласованность внутри заявленного measurement range, не требовать невозможной инвариантности при quantization/изменённом SNR.

**Готово, когда:** two-pass имеет измеримое преимущество либо обоснованно остаётся optional. Если простая схема столь же точна на development set, выбирать более простую; это не нарушение цели проекта.

**Шаг 17. Полярность: одинаковые правила для обоих знаков**

Обе полярности v2 проходят идентичный полный путь, включая одинаковую dedup и refinement. Исключить третий анализ победителя с другим набором recovery rules. Сохранять оба результата/score, выбранный знак, основания и margin.

Не награждать score за одно лишь увеличение числа событий или соответствие stimulus frequency. Регулярность не должна гарантировать правильную полярность. Autocorrelation не использовать как независимый discriminator знака: для x и −x при одинаковой обработке она одинакова.

Симметричный trace может иметь одинаково обоснованные фазы. При неразрешённом выборе — REVIEW; если count одинаков, отдельно отметить устойчивость count и неопределённость timestamps. `margin` не называть вероятностью accuracy без калибровки. Добавить явный logged override `auto/positive/negative`.

**Проверки:** инвертированные копии asymmetric traces сохраняют times/count; ambiguous sine даёт ambiguity; нерегулярные качественные события не проигрывают только из-за CV; manual override работает и сохраняется в metadata. В diagnostics periodicity читается из реального ключа и не теряется как NaN из-за неправильного доступа.

**Шаг 18. Единый QC для v2**

Собрать решения из preprocessing/analysis в понятный QC module. Сохранить все причины и выделить hard errors, technical rejection, review warnings и descriptive rhythm features. Убрать зависимость пригодности от числа Excel-строк.

Технические признаки: time/fs validity, coverage, overlap conflict, clipping, discontinuities, invalid support, local noise, sampling resolution. Детекторные: polarity ambiguity, unresolved pairs, insufficient seeds и sensitivity instability. IBI CV, amplitude variation, pauses и periodicity отображаются отдельно и не являются автоматическим доказательством шума.

Проверить небольшие изменения detection thresholds, например ±10–15%, как stability diagnostic. Зафиксировать, что именно сравнивается: число и соответствие event times. Не переименовывать instability в biological abnormality. Для каждой новой числовой границы нужна development evidence и версия профиля; не переносить узкие legacy conditions без обоснования.

**Проверки:** нерегулярный чистый trace не отбрасывается только из-за нерегулярности; noise не проходит только из-за quasi-periodicity; mixed/ambiguous morphology вызывает review; ошибка входа остаётся ERROR. Изменение QC не уничтожает raw/candidates для проверки. После шага все tests v2 для времени, counts, polarity и outputs проходят вместе.

**Шаг 19. Валидация и решение о переходе**

Это обязательная зависимость переключения основного метода, а не разрешение писать код только после получения данных. Все предыдущие независимые исправления можно выполнить заранее.

Собрать реальные записи разных клеток/подготовок/дней, fs, амплитуд, длительностей, stimulated/spontaneous условий. Разметить уверенные events, ambiguous events и invalid intervals; при необходимости использовать видео. Установить операциональное определение отдельного contraction без классификации AFC. Желательно независимое размечивание и разрешение разногласий.

Разделение development/holdout делать по независимой экспериментальной единице, не по соседним сегментам одной записи. На development выбирать параметры и допустимое timestamp matching tolerance; заморозить их до holdout. Matching one-to-one, а не подсчёт каждого predicted peak как верного рядом с одной и той же меткой.

Сравнить audited baseline, исправленный legacy и v2 на одинаковых входах и одинаковом endpoint. Отдельно показать эффект исправления времени и эффект замены detection. Метрики: event precision/recall/F1, count error, Hz/BPM error/bias, ×2/÷2 errors, polarity correctness/ambiguity, PASS/REVIEW/REJECT/ERROR fractions, качество среди автоматических PASS. Не скрывать difficult cases за их исключением.

Критерии приемки численно зафиксировать до holdout, исходя из задачи лаборатории. Не выдумывать в плане универсальные 99%. Если после holdout параметры меняются, этот набор больше не является нетронутой финальной проверкой; обновить evaluation protocol честно.

**Готово, когда:** подготовлен воспроизводимый comparison report, перечислены исправленные/сохранённые/новые ошибки, достигнуты согласованные критерии. Отсутствие реальных данных = blocked для scientific validation и перехода по умолчанию, а не «всё протестировано на synthetic».

**Шаг 20. Переключение и удаление старых каскадов**

После шага 19 сделать v2 основным единственным production-путём. Удалить rowwise peak detection, gap/transient fill, boundary rescue, повторные dedup и связанные config/debug branches, если их задачи теперь покрыты новым методом. Старую версию сохраняет Git; development comparison можно вынести в benchmark tooling, не оставлять скрытый production fallback.

Проверить остаточные функции восстановления близких вторых максимумов: в новом методе они не должны сохраняться под нейтральным именем с прежней биологически неоднозначной семантикой. Все события подчиняются одному правилу и одной mask policy.

**Проверки:** после удаления legacy v2 outputs полностью совпадают с validated v2 до удаления. CLI использует новый метод явно; нет внезапного перехода на legacy при ошибке. Все assertions accepted count↔events↔audit↔report проходят. Не должно остаться xfail по исправляемым дефектам.

**Откат:** вернуть предыдущий проверенный commit/ветку, а не менять thresholds наугад. Исторические результаты помечены detector version; не смешивать версии в одной итоговой выборке незаметно.

**Шаг 21. Простой запуск и проверка сомнительных результатов**

CLI принимает workbook или batch input, output directory и небольшой набор понятных параметров. Debug по умолчанию выключен; флаг реально включает его. Добавить headless-friendly imports: core analysis не должен требовать AFC GUI или DOCX при отсутствии запросов на отчёт. Оставить привычный DOCX, если он нужен лаборатории; смена на HTML необязательна.

Минимальный review обычных событий: посмотреть сомнительный сегмент, подтвердить/исключить peak, добавить пропущенное наблюдаемое событие, переключить polarity, пометить invalid interval. Добавленный event должен соответствовать наблюдаемым данным и иметь provenance; запрещено добавление в gap как измеренного сокращения. Не создавать классификатор AFC.

Automatic result сохраняется неизменным; review — отдельный слой с input hash, method/config version, timestamp, action и reason. Повторное открытие чужого/изменённого input не должно молча применять старые corrections. Пересчёт reviewed metrics использует тот же модуль шага 12 и явно помечает reviewed result.

**Проверки:** cancel review не меняет auto result; save/reload воспроизводим; изменение input hash даёт конфликт; manual edit обновляет count и frequency согласованно; batch идентифицирует каждый sample. Сотрудник может выполнить example по README без редактирования Python.

Этот шаг можно разделить на 21a CLI и 21b review. Если в первом релизе review отсутствует, ambiguity должна оставаться явно REVIEW, а ограничение — документированным; нельзя выдавать неподтверждённые результаты за PASS ради завершения интерфейса.

**Шаг 22. Подготовка релиза**

Добавить минимальный `pyproject.toml`/entry point, version, проверенный dependency set, CI на поддерживаемых платформах, changelog, input schema, usage guide и example с ожидаемым результатом. Windows важен для лабораторного запуска; headless smoke-test — для reproducibility. Не обновлять без необходимости весь dependency stack на этом шаге.

Экспортировать run metadata: input SHA256, code version/commit, detector profile/version, Python/dependency versions, arguments, timing/coverage conventions, manual review state. Источник и output schema версионировать. Лицензию определить с владельцем, citation metadata заполнить фактическими данными; не придумывать DOI, авторов или согласование учреждения.

**Финальные критерии:** AFC отсутствует в рабочем продукте; input никогда не перезаписывается; error≠zero; время сохраняет gaps; output согласован; synthetic invariants проходят; real-data validation завершена в заявленном диапазоне; установка и пример проверены в чистой среде; ограничения описаны. Известные неустранённые дефекты, затрагивающие частоту, блокируют заявление о validated release.

Подготовка релиза не означает автоматическую публикацию GitHub release или экспериментальных данных. Публиковать только в рамках соответствующего поручения пользователя; fixtures не должны раскрывать неразрешённые данные.

**Если обнаружилась новая проблема**

Сначала сохранить минимальный воспроизводимый пример и классифицировать её: data contract, timing, detector, polarity, QC, export или UI. Не менять несколько уровней одновременно.

Если дефект в текущем scope — исправить и добавить regression test до завершения шага. Если затронута уже исправленная инварианта — текущий шаг не принимать, найти первое изменение, которое её нарушило. Если проблема относится к будущему этапу, записать отдельный issue с reproduction и временным явным статусом; не прятать её blanket exception или auto fallback.

Не ослаблять тест, не менять эталон без доказательства, не увеличивать tolerance только ради green CI. Для scientific method discrepancy нельзя назначать правоту старому/новому детектору по числу событий: нужна разметка или известная synthetic truth. Если требуется новый threshold, проверить весь development-набор, а не единственный проблемный файл.

Для сохранения поведения после pure refactor изменения accepted events должны быть нулевыми. Для bug fix составить таблицу affected fixtures с before/after/expected/reason. Для нового метода составить comparison report и не смешивать его с silent baseline update.

Откат делать через обычный revert/возврат к проверенной ветке без удаления пользовательской работы. Не применять destructive reset, force push или очистку исходных/экспериментальных файлов как часть этого плана.

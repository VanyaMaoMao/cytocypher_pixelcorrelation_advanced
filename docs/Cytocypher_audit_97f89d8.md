## 1. Время и формат экспорта — высокий приоритет

Места: `pixel_counter/preprocessing.py:334` (`build_concatenated_signal`), особенно около 430 и 501; `docs/input_schema.md`; `pixel_counter/io_utils.py:15`.

В реальных файлах `Begin (seconds)` задаёт начало сегмента; `Begin` изменяется по transient-окнам. Документация ошибочно описывает `Begin (seconds)` как начало данных строки и называет y-offsets микрометрами. Подтверждения пространственных единиц нет: эти колонки используются как отсчёты временного сигнала.

Наблюдение по данным: если привязать `Begin` к первому конечному значению строки, перекрывающиеся исходные samples совпадают во всех проверенных сегментах обоих файлов. Это подтверждённая закономерность этих fixtures, а не доказательство универсальности для любого экспорта. Нужно уточнить формат у экспортирующей программы и закрепить правило тестами. Внутренние пропуски при этом нельзя удалять.

Текущий код размещает всю строку, включая начальные пустые ячейки, начиная с Begin. Начальные пустоты есть в 11 сегментах двух файлов; максимум 11 samples, то есть 44 ms при 250 Hz. Затем код компенсирует расхождения перекрытий медианным смещением строки и усреднением. Максимальный внесённый offset: 0.092 для файла 24 сентября и 0.1895 для файла 25 сентября. Последнее обнаружено в Segment 42. Это показывает, что сшивка реально меняет значения, а не только удаляет повторные samples.

Шаг 10 в commit `4a9a67e` изменил одну строку production-кода: `np.empty` на `np.full(...,-1)`. Старая коррекция baseline и partition по строкам сохранились. Сам по себе sentinel полезен, но не выполняет все требования coverage, overlap conflict, nested windows и valid blocks.

Критерии исправления:

1. Документировать anchor времени и политику краевого padding для подтверждённого формата.
2. Проверять перекрытия до коррекции. Одинаковые значения учитывать однократно; конфликт регистрировать, а не скрывать offset-коррекцией.
3. Сохранять observed mask, valid blocks и несколько source rows для overlap.
4. Проверить вложенные/повторные окна, перестановку строк, настоящий gap и эквивалентные разбиения.
5. Согласовать точность округления timestamps (в файлах есть округление на 0.0001 s).

## 2. NaN сохранён в массиве, но downstream не адаптирован — высокий приоритет

Места: `qc.py:20`, `preprocessing.py:130,148,153`, `_analyze_prebuilt_signal`.

Синтетический контроль: 10 s, fs=250, десять Gaussian peaks A=0.2, sigma=0.035 s, centers 0.5+k, шум SD=0.0005, RNG=12, строки по 250 samples. Чистая версия: 10 событий, PASS, SNR≈3.0737, 0 vertical artifacts. Вторая версия отличается только `signal[750:775]=NaN`, то есть 0.1 s вдали от пиков: 0 событий, REJECT `dominant_vertical_line_artifacts`, SNR=NaN, 587 отметок артефактов.

Причина: статистики через обычные percentile/median/MAD получают NaN; сравнения с NaN в artifact detector не работают как корректный порог. `_rolling_quantile_trend` также строит trend через интерполяцию gaps; конечный signal сохраняет NaN, но оценки тренда уже не ограничены finite blocks. Некоторые вычисления по строкам удаляют non-finite samples для анализа.

Критерий: пропуск не должен превращаться в сотни артефактов. Допустим анализ отдельных valid blocks либо явный статус unsupported missing-data policy, но с правдивой причиной. Нельзя восстанавливать время удалением внутренних NaN. IBI через gap запрещён.

## 3. Канонический реестр событий неполон — высокий приоритет

Места: `analysis.py:128` (`_build_peak_debug_rows`), `analysis.py:1130` (`build_events_dataframe`), `results.py:440`, `workbook.py:145`.

Debug по-прежнему строится только циклом по initial raw candidates. Rescue, отсутствующий в initial set, не попадает в общий debug.

| Файл | Сегмент | Принятые события | Rescue по metadata | Принятых событий нет в debug |
|---|---:|---:|---:|---:|
| 24 сентября | 18 | 11 | 8 | 1 |
| 24 сентября | 24 | 19 | 10 | 5 |
| 25 сентября | 29 | 19 | 10 | 3 |
| 25 сентября | 42 | 12 | 3 | 1 |

Итого десять принятых событий отсутствуют в общем debug. Rescue-аудит отдельно может содержать их; проблема именно в отсутствии единого полного реестра.

Дополнительный probe: один candidate sample передан как main и rescue. `build_events_dataframe` создаёт две строки с одним event_id. В реальных 90 сегментах дубли event_id не обнаружены; это дефект защиты инварианты, подтверждённый отдельным входом.

`_make_summary_dataframe` вообще не добавляет Sample ID. Auto-only записывает именно этот DataFrame напрямую, поэтому Sample ID до основной summary не доходит, хотя присутствует в events/meta.

Критерии: один candidate sample — одна сущность с объединённым provenance; каждый accepted event существует в audit; N=число уникальных accepted IDs=число accepted event rows; QC-rejected preliminary candidates не маркируются окончательно accepted; Sample ID присутствует в summary/events/audit. Источник файла должен входить в идентичность при объединении нескольких workbooks.

## 5. Частота зависит от разбиения строк — воспроизведённый legacy-дефект

Места: `analysis.py:43`, `analysis.py:262`, `analysis.py:653`, QC по n_rows.

Точный контрпример плана: fs=250 Hz, duration=10 s, Gaussian A=0.2, sigma=0.020 s, centers 0.125+0.25*k, k=0..39, шум SD=0.0005, RNG=42. Один signal, меняется только число samples в строке.

| Samples/row | Истина | Найдено | BPM | QC |
|---:|---:|---:|---:|---|
| 125 | 40 | 36 | 216 | PASS |
| 250 | 40 | 24 | 144 | PASS |
| 500 | 40 | 21 | 126 | PASS |
| 2500 | 40 | 0 | 0 | REJECT: too_few_rows |

Существование этого дефекта до шагов 14–18 ожидаемо. Проблема шага 01: regression-набор не фиксирует его. Не чинить новый детектор вперемешку с удалением AFC. Сначала добавить воспроизводимый strict xfail с плановым этапом, затем исправить глобальной детекцией и единой дедупликацией. Итоговый критерий — 40 событий с правильными временами, а не одинаковое неверное число.

В дедупликации окно 0.28 s и исключение double-lobe зависят от принадлежности обоих candidates одной transient row. Это нарушает независимость от экспорта. Recovery/coherence также используют количество и границы строк.

## 6. Два разных знаменателя BPM — будущий шаг 12 обязателен

Места: `run_pixel_analysis.py:42–43`, `analysis.py:2281`, `analysis.py:2776`, `results.py:440`, `reporting.py:269`.

CLI фиксирует stimulation=1 Hz и duration=10 s. Входные сегменты около 5 s. Detector делит N на длину stitched array/fs, summary и текст DOCX — на recording_s.

Реальный пример: файл 25 сентября, Segment 1, N=5. Detector сообщает 63.83 BPM при duration=4.700 s. Summary с текущими CLI-параметрами даст 30 BPM. Различие вызвано знаменателями; ни один из них нельзя автоматически объявлять правильной полной частотой при неполном покрытии.

Нужно разделить recording_span, observed_duration, analyzed_duration и coverage. Выбранные transient-окна могут быть неслучайной выборкой. До подтверждения механизма экспорта нельзя переносить rate по окнам на всю запись. Recording duration override не должен молча противоречить metadata. Stimulation не является ground truth и не должна подгонять count.

## 7. ERROR/REJECT исправлены не во всех представлениях

Summary корректно отделяет Accepted BPM/events от Diagnostic и использует NaN при REJECT/ERROR. Но DOCX всё ещё сводит QC к PASS/REJECT и печатает нулевой BPM для отклонённых/ошибочных сегментов. Часть поздних QC-отказов происходит после заполнения debug labels main/rescue, затем возвращаются пустые events и N=0.

Нужен единый segment status/result для всех outputs, с сохранением preliminary candidates. Это довершение шага 03 и зависимость шагов 12–13. Не объявлять hard error биологическим нулём.

## 8. Валидация входа и безопасная запись частичны

- Missing fs, полностью NaN fs и текст `oops` в fs принимаются как 250 Hz. Воспроизведено через parser с DataFrame. Нет явного override и provenance fallback.
- y-offsets сортируются, но проверка равномерной сетки и пропущенных позиций отсутствует: y0/y2 принимаются как два соседних значения. Необходимо либо определить разрешённые labels, либо сохранять/отклонять отсутствующий offset согласно контракту.
- `check_output_conflicts` проверяет outputs против input, но принимает два одинаковых output paths. Разные writers способны перезаписать результат друг друга.
- Auto-only summary пишет напрямую `summary_df.to_excel`, обходя atomic helper. Diagnostics summary — тоже напрямую.
- Часть writers действительно атомарна; Path/samefile защита input полезна. Исправлять конкретные оставшиеся пути.

## 9. Полярность, QC и интерфейс — остаются задачи плана

- Обе полярности оцениваются без close-peak recovery, победитель запускается третий раз с recovery=True. Финальный result не идентичен сравнивавшемуся candidate.
- `_quality_score` награждает число peaks до 12 и штрафует IBI CV. Это не калиброванная вероятность правильной ориентации.
- `candidate_metrics` читает `periodicity` из верхнего meta, тогда как значение находится в `sheet_qc.periodicity_score`; диагностика теряет показатель.
- QC использует число строк и свойства ритма. REVIEW не является полноценным итоговым статусом.
- На графике prominence thresholds рисуются как абсолютные horizontal amplitude lines.
- CLI всегда передаёт debug=True и debug_peak_trace=True; флаг управляет только дополнительной печатью путей.
- Core импортирует plotting/reporting через пакет; headless-friendly optional imports пока не реализованы.
- Нет pyproject/entry point и CI в tracked files; pytest отсутствует в requirements. Это частично шаг 01, частично будущий шаг 22.

## 10. Насколько полезны текущие тесты

Проверки IO, fs conflicts, Sample ID, сортировки y-columns, NaN position, sentinel и exit codes полезны. Но 28 passed не означают выполнение плана:

- `test_basic.py` содержит assert True.
- Integration test проверяет существование dummy_input и непустой DataFrame, не count, status или timestamps.
- Генератор dummy использует нефиксированный RNG и по одному y-value на строку; это слабый научный эталон.
- Canonical-event tests проверяют колонки и простые раздельные main/rescue, но не missing rescue audit, duplicate candidate, rejected segment и соответствие N.
- Overlap test проверяет длину/NaN и конечность, но не сохранение точных значений, конфликтов и provenance.
- Нет автоматического comparison report по реальным fixtures; нет scientific ground truth для них.

Минимальная модель synthetic truth для отдельного regression test:

```python
fs = 250.0
t = np.arange(2500) / fs
centers = 0.125 + 0.25 * np.arange(40)
signal = sum(0.2 * np.exp(-0.5 * ((t - c) / 0.020) ** 2) for c in centers)
signal += np.random.default_rng(42).normal(0, 0.0005, len(t))
# Разбить тот же signal на строки по 125, 250 и 500 samples.
# Begin каждой строки = исходный индекс / fs; не менять samples.
# Ожидается 40 событий и соответствие временам centers в заданном допуске.
```
